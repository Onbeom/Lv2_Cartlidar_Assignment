# 4단계 ROS 연동 검증 계획 (초안, 2026-10-25, 승인 전)

상태: **승인(사용자 2026-10-25): L1·L2 기준 그대로, 4장 결정은 모두 권장안**(조건 B 포함, `/odom` (a) Isaac 계산, 팔 카메라 640×480, IR 좌우는 cuVSLAM 단계로). 모두 **모의 시험**(Isaac Sim)이다.

## 0. 배경 (코드·문서에서 확인한 것)

- Isaac Sim 6.1.0.0(pip, `~/isaacsim-venv`)의 `isaacsim.ros2.core`는 셸에 `ROS_DISTRO`가 있으면 그 배포판을 쓴다. 내장 라이브러리는 `humble`·`jazzy`뿐이다. `lyrical`은 공식 지원 목록(`SUPPORTED_ROS_DISTROS`: 22→humble, 24→jazzy)에 없어서 "[Experimental] not an officially supported distribution" 경고를 내고, 시스템 `/opt/ros/lyrical` 라이브러리와 시스템 rclpy를 불러오려고 한다(`impl/extension.py` 53~136행). `ROS_DISTRO`가 없으면 Ubuntu 24 → 내장 `jazzy`를 쓴다.
- 운영 측 예제(waffle-lyrical-slam README 100·125행)는 6.1 + Lyrical에서 **CameraInfo의 K/R/P가 한 칸씩 밀리는 것**을 확인했다. 원인은 Lyrical의 sequence 구조체에 필드가 추가된 것이다. 다른 메시지는 확인하지 않았다고 적혀 있다.
- 브리지 C++ 노드는 Jazzy 헤더로 빌드됐고, Lyrical rmw는 Lyrical 형식 정보로 메모리를 읽는다. 그래서 **"메시지 안에서 기본형 sequence 뒤에 오는 필드는 sequence 하나당 8바이트 밀린다"**는 가설을 세운다(CameraInfo는 `d` 뒤의 K/R/P가 밀림). 이 가설이 맞다면:
  - Image(`data`가 마지막), TFMessage(`transforms` 하나), Odometry(고정 배열), Twist·Clock은 정상이다.
  - LaserScan의 `intensities`(`ranges` 뒤)와 JointState의 `position`·`velocity`·`effort`(`name` 뒤)는 깨진다.
- 10-13에 만든 `bridge_check/`(최소 장면, B0~B3)는 판정 기준을 사용자에게 확인받았지만 실행하지 않았다. 당시 대상은 `~/isaacsim` rc.26과 도메인 28이었고, 고칠 목록이 대기 중이었다(TF 대상 prim, CSV 즉시 기록, RSS 측정 PID, 오류 보고 업로드 끄기, CPU 4스레드, empy·lark 경로).
- 팀 인터페이스(`interfaces.md`): `/cmd_vel`은 **TwistStamped**다. Isaac의 `ROS2SubscribeTwist`는 Twist만 받으므로 범용 `ROS2Subscriber` 노드로 TwistStamped를 받는다. 인지 파트가 받는 토픽은 `perception.yaml`과 `lidar.yaml`에 있다(아래 L2 표).

## 1. 구성

| 단계 | 장면 | 목적 | 필수 여부 |
|---|---|---|---|
| L1 | 최소 장면(벽 1개, 카메라 2, 2D 라이다 1, 고정 TF·Odometry) | 브리지 자체의 동작과 메시지 형식별 깨짐 확인 | (필수) 0번 검사 |
| L2 | Waffle 4WD USD 261022_2119(v12 조건) + 평지 + 확인용 벽·표식 | 첫 검사 1~5를 로봇으로 확인. 인지 파트 토픽 이름·frame 그대로 | (필수) L1에서 발행 방식이 정해진 뒤 |

조건(L1):

- **A**: `source /opt/ros/lyrical/setup.bash` 뒤 Isaac 실행. 시험 대상인 native Lyrical 브리지다. (필수)
- ~~**B**: source 없이 실행(내장 Jazzy). Jazzy↔Lyrical 비교 기준.~~ **뺌(사용자 2026-10-25: 환경은 Lyrical만 쓴다).** 짧은 실행에서 Lyrical 관찰 노드가 B 발행자를 찾지 못한 기록은 6장에 남긴다. 실행기의 B 경로는 지우지 않고 쓰지 않는다.
- **A′(A2)**: A + `bridge_check/pylinks/`(시스템 python3-empy 3.3.4·python3-lark 1.1.9 링크)를 PYTHONPATH 앞에 둠. CameraInfo helper가 `em`을 쓰기 때문. (사용자 승인 2026-10-25, 10-13 ① 방식)
- **공식 L1 절차(사용자 승인 2026-10-25)**: A′로 세 번 나눠 돌린다. ① `--skip=camera_info,scan` 60 s(TwistStamped 범용 구독 → B2-11), ② `--skip=stamped,camera_info` 60 s(LaserScan → B2-7·B2-8), ③ `--skip=stamped,scan` 600 s(나머지 전부, B3 포함). 짧은 실행 ①②의 B3(600 s) 항목은 판정에 쓰지 않는다. 로그의 `libisaacsim.ros2.core.lyrical.so` 없음 안내 줄은 B0 오류에서 빼고 '기록'으로 센다.
- 모든 조건은 `env -i`로 같은 환경에서 시작한다. `ROS_DOMAIN_ID=26`, CycloneDDS, `ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST`, `--/crashreporter/url=`.

## 2. L1 판정 기준과 예상

기존 기준(10-13 확인)은 그대로 둔다: 받은 개수 ≥ 95 %, 끊김 = 평소 간격 3배 초과 0회, 라이다 벽 2.00 ± 0.02 m, TF ±1e-4 m·rad, Odometry 위치 ±1e-3 m, K 상대 오차 ≤ 1e-4, Twist 차이 ≤ 1e-6, 재생 ≥ 600 s. **★ 표시는 새로 넣는 항목**이다.

| 번호 | 항목 | 기준 | 예상 (A / B, 이유) |
|---|---|---|---|
| B0-1 | 사용한 배포판·라이브러리 위치 | A: `/opt/ros/lyrical`에서 rcl·rmw를 읽음 / B: 내장 jazzy | A 성공, 경고 1줄(Experimental) / B 성공 |
| B0-2 | ROS 관련 오류·심볼 미해결 | 0줄 | A·B 성공. 심볼 이름은 배포판 사이에 같다고 봄 |
| ★B0-3 | 시스템 rclpy 로드 | 기록(실패여도 판정 실패 아님) | A: 실패 경고 가능(venv에 empy·lark 없음) |
| B1 | `/clock` 진행, 거꾸로 0회, 일시정지 중 정지, 재개 후 진행 | 모두 | A·B 성공. Clock은 고정 구조체 |
| B2-1 | Image 크기·encoding·step·길이·frame_id | 모든 메시지 | A·B 성공. `data`가 마지막 필드 |
| B2-2 | CameraInfo 크기·fx·fy·cx·cy·frame_id | 모든 메시지 | **A 실패**(K 밀림, README와 같음) / B 성공 |
| ★B2-3 | CameraInfo `d` 길이·`r` 단위행렬·`p`(오른쪽 P[3] = −fx × 0.05) | 모든 메시지, 상대 오차 ≤ 1e-4 | A 실패 / B 성공 |
| B2-4 | Image·CameraInfo stamp 일치 | ≥ 95 % | A·B 성공 |
| B2-5 | `/tf` world→base_link | ±1e-4 | A·B 성공 |
| ★B2-6 | `/tf` 한 메시지에 변환 2개(대상 prim 2개) | 둘 다 ±1e-4 | A·B 성공. sequence 하나만 있음 |
| B2-7 | `/scan` ranges 개수·정면 거리·frame_id | 모든 메시지 | A·B 성공. `ranges`가 첫 sequence |
| ★B2-8 | `/scan` `intensities` 길이 = `ranges` 길이(또는 0), 값이 유한 | 모든 메시지 | **A 실패 또는 Isaac 비정상 종료**(가설: 8바이트 밀림) / B 성공 |
| B2-9 | `/odom` frame·위치·자세·covariance 길이 36 | 모든 메시지 | A·B 성공. 고정 배열 |
| B2-10 | `/cmd_vel`(Twist) 받은 값 | 차이 ≤ 1e-6 | A·B 성공 |
| ★B2-11 | `/cmd_vel_stamped`(TwistStamped, 범용 구독 노드) 받은 값 | 차이 ≤ 1e-6 | A 불확실(범용 노드는 동적 형식 지원 경로가 다름) / B 불확실 |
| B3 | 600 s 동안 받은 개수·끊김·종료 코드 0·메모리 증가(표시만) | 위 기준 | A·B 성공. B2-8에서 비정상 종료하면 A 실패 |

L1 결과를 보고 L2의 발행 방식을 정한다. 이 결정은 결과를 본 뒤 사용자에게 묻는다:

- A가 모두 성공하면 → native Lyrical 브리지만 쓴다.
- A의 일부 형식만 실패하면 → 그 형식만 이 프로세스 안의 Lyrical rclpy로 발행한다(README 방식, venv에 `empy==3.3.4`·`lark==1.1.9` 필요). 실패한 형식은 판정표에 그대로 남긴다.
- B만 성공하면 → 내장 Jazzy + DDS 연결은 "native Lyrical"이 아니라고 따로 적고 대안으로 둔다.

## 3. L2 판정 기준과 예상 (첫 검사 1~5)

발행 토픽(인지 파트 설정의 이름·frame을 그대로 쓴다):

| 토픽 | 형식 | frame_id | 비고 |
|---|---|---|---|
| `/clock` | Clock | - | |
| `/scan_front`, `/scan_rear` | LaserScan | `lidar_front_scan`, `lidar_rear_scan` | 인지 scan_merger 입력 |
| `/top_camera_{front,rear}/color/image_raw`·`/camera_info` | Image·CameraInfo | `top_camera_*_color_optical_frame` | |
| `/top_camera_{front,rear}/aligned_depth_to_color/image_raw` | Image(32FC1 또는 16UC1) | 같은 컬러 frame | 컬러와 크기 같음 |
| `/arm_camera/image_raw`·`/camera_info` | Image·CameraInfo | `camera_optical_frame` | 해상도는 결정 4 |
| `/joint_states` | JointState | - | 관절 11개 |
| `/odom` + TF `odom→base_footprint` | Odometry·TF | `odom`→`base_footprint` | 결정 3 |
| `/cmd_vel` (받기) | TwistStamped | - | 팀 인터페이스 |

고정 TF(`base_footprint` 아래 전부)는 `robot_state_publisher`(URDF 261022_2119 + `/joint_states`)만 발행하고, Isaac은 `odom→base_footprint`만 발행한다.

| 번호 | 항목 | 기준(제안) | 예상 |
|---|---|---|---|
| C1-1 | `/clock` 진행, 거꾸로 0회 | 모두 | 성공 |
| C1-2 | 모든 관찰·ROS 노드의 `use_sim_time` | `true` (`ros2 param get`으로 확인) | 성공. launch에서 설정 |
| C2-1 | 위 토픽이 모두 들어옴, 받은 개수 | 설정 주기 대비 ≥ 95 %(L1과 같음) | 카메라는 **불확실**: 8 GB VRAM에서 컬러 3 + 깊이 2를 렌더해야 함. GPU 메모리를 함께 기록 |
| C2-2 | 영상 지연(받은 순간 `/clock` − stamp) | 100 % ≤ 0.3 s(인지 `frame_max_age_s`와 같음), p95 기록 | 성공 |
| C2-3 | 라이다 방향: 앞 1.0 m 벽, +y 쪽 상자 | 정면 거리 = 계산값 ± 0.02 m, 상자가 +각도 쪽에 보임(앞·뒤 각각) | 성공. scan 프레임 roll π가 반영된 2119 기준 |
| C2-4 | 카메라 방향·깊이: 정면 벽, 왼쪽 색 표식 | 표식이 영상 왼쪽 절반에, 중앙 깊이 = 계산값 ± 0.02 m | 성공 |
| C2-5 | `/joint_states` 이름 11개·위치 | 접은 자세 S0에서 각 관절 = 시뮬레이션 값 ± 1e-3 rad | L1 결과에 따라 다름. 가설대로라면 native A에서는 위치가 밀림 |
| C3-1 | `odom`에서 인지가 쓰는 frame까지 TF 조회 | `base_link`, 카메라 optical frame 3개, scan frame 2개. 10 s마다 조회해 실패 0회 | 성공 |
| C3-2 | 같은 TF를 두 노드가 발행하지 않음 | 자식 frame마다 부모 1개, 발행 노드 1개(`ros2 topic info /tf -v`와 받은 기록) | 성공 |
| C4-1 | 같은 카메라의 컬러·깊이·CameraInfo stamp | ≥ 95 % 일치(L1과 같음) | 성공 |
| C4-2 | CameraInfo K = USD 카메라 값 | 상대 오차 ≤ 1e-4 | L1 결과에 따라 다름 |
| C5-1 | `/cmd_vel` → 바퀴 목표 속도 | 바퀴마다 기구학 계산값과 차이 ≤ 1e-6 rad/s(전달 확인) | 성공 |
| C5-2 | 직진 0.10 m/s 5 s | 실제 이동 0.50 ± 0.025 m(5 %), 옆 ≤ 0.02 m, yaw ≤ 2° | 성공. P6(0.2 m에서 0.1993/0.2006) 근거 |
| C5-3 | 제자리 회전 +0.5 rad/s 4 s | 회전 방향 부호가 맞음(반시계 = yaw 증가). 회전량은 기록만 | 성공. 회전량은 V 시험처럼 명령보다 14~23 % 적을 것(미끄럼) |

## 4. 사용자가 정할 것

1. L1 기준(위 표, ★ 새 항목 포함)과 L2 기준(제안 값) 승인
2. L1 조건 B 포함 여부 (선택 · 권장: A가 깨질 때 대안을 같은 실행에서 확인할 수 있다)
3. L2 `/odom` 출처: (a) Isaac 차체 속도로 계산(`IsaacComputeOdometry`, 참값 기반) (선택 · 권장: 이번 단계는 전달 확인이 목적이고, 바퀴 오도메트리 노드는 팀 구조상 diff_drive_controller 몫이라 따로 만든다) / (b) 바퀴 회전으로 계산하는 노드를 지금 만든다 (선택 · 비권장: 오도메트리 오차가 섞여 전달 문제와 구분이 안 됨)
4. 팔 카메라 해상도: (a) 1920×1080(인지 설정 그대로) + 사용자가 `net.core.rmem_max`를 올림(sudo) / (b) 이번 검사는 640×480, 1080p는 따로 (선택 · 권장: 6.2 MB 영상이 4 MB 수신 버퍼를 넘어 버려지는 문제가 이미 확인됐고, 8 GB VRAM 부담도 줄어든다)
5. RealSense 적외선 좌우(infra1·2) 발행: 이번에는 빼고 cuVSLAM 단계에서 (선택 · 권장: 인지 파트는 컬러·깊이만 쓴다)

## 5. 실행 순서 (승인 뒤)

1. `bridge_check/`를 이 폴더로 복사해 고친다(원본 10-13판은 그대로 둔다). pip 경로·도메인 26·대기 중이던 수정·★ 항목을 반영한다.
2. 도구 확인: Isaac 없이 관찰 노드만 Lyrical로 실행하고 문법을 검사한다.
3. 사용자가 L1 A(·B)를 실행한다(각 약 11분). → 판정표, 결과 위치 `261025_0307/results/L1_*`
4. L1 결과로 발행 방식을 정한다(사용자 결정) → L2 장면·launch 작성 → 사용자가 L2를 실행한다.
5. 결과를 인지 파트 최신 세션([인지 파트 코드 38차 R4])에 알리고, STATUS와 변경요약을 갱신한다.
